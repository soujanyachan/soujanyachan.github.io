    First, you will likely see DevOps talk about software development for the most case. The fact is DevOps isn't ONLY Software Development. It also can be Infrastructure Management. You can have one, or the other, or both. (Software Development / Infrastructure Management).

When I say Infrastructure Management, I mean like Servers, VMs, Containers, networking, storage, whatever. You CAN use DevOps to do all that shit. You may not want to, but you can.

    Second, DevOps has three facets to it (that are different from how traditional IT/software development is done):

    Business Process
    Culture
    Technology used

Each of these need to adapt when moving to DevOps as a practice. Practice as in, an over-arching way of doing things.

Business Processes change, in that you can make changes, create new things, typically faster, correct failures faster. So it becomes more of a "what do we want" and less of a "how long will this take". So Business Processes need to be adapted to shift away from Change Management (as well as other things), because DevOps automatically mitigates the risks of Change by enabling "failing fast" and correcting those failures rapidly too. The risk is reduced/mitigated, removing the justification for traditional Configuration Management. There's plenty more here too.

Culture change, in that how the staff (technical, AND non-technical) think about what they want to achieve shifts. In similar vein of "when/how" to "what do we want". This doesn't exactly make DevOps/you a silver bullet, or a miracle worker. But it enables you to innovate/produce faster, and keep up with the "demands of humans", instead of "humans waiting for IT".

Technology used change, this primarily is about shifting from like, booting from ISOs to install an OS, or using a golden image, or installing software by hand, to moving to IaC (Infrastructure as Code). Defining everything as code, so that if you want to make changes, you just change text in a file and it gets applied. Or copy that same code into another yaml file and provision a new server/container/whatever. It reduces error, speeds up provisioning/changing, and so much more. This can look like many different things.

None of this requires the use of a public cloud. You can do all of this self-hosted, or cloud, or whatever. It's conceptual, and not tied to specific products, etc.
